# Безопасное создание первого администратора

Обычный запуск сайта, `npm run dev`, `npm start` и перезапуск PM2 **не создают пользователей**. Стандартного логина и пароля нет. Инициализация каталога не назначает права администратора.

## Новый магазин: в БД ещё нет пользователей

1. Подготовьте схему БД по инструкции установки. До создания администратора не открывайте регистрацию для посетителей.
2. Войдите в SSH-терминал владельца сервера и перейдите в каталог **нужного магазина**. Команда использует те же настройки БД из окружения и `.env`, что и сайт: `USE_NEON=true` + `DATABASE_URL` для Neon, либо `PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD`, `PGDATABASE` для PostgreSQL. Переменные окружения имеют приоритет над `.env`.
3. Запустите:

   ```bash
   npm run bootstrap:admin
   ```

4. Введите свой логин (3–50 символов: латинские буквы, цифры, точка, дефис или подчёркивание; начало — буква или цифра). Он будет сохранён в нижнем регистре.
5. Введите и подтвердите уникальный пароль из менеджера паролей: 16–256 символов, минимум три типа символов из строчных букв, заглавных букв, цифр и специальных символов. Пробелов по краям быть не должно. **Ввод скрыт**.

Пароль не попадает в историю команд, `.env`, аргументы процесса или журнал. Только временные переменные дочернего процесса `BOOTSTRAP_ADMIN_USERNAME` / `BOOTSTRAP_ADMIN_PASSWORD` передают данные команде; после выхода они удаляются. В БД записывается только хеш с индивидуальной солью, совместимый с обычным входом.

Для автоматизации разрешены эти две временные переменные через защищённое окружение запуска. Не пишите их значения в команды, историю shell, PM2-конфигурацию, репозиторий или чат. Не используйте `SUPER_ADMIN_PASSWORD` как пароль обычного администратора: скрытый супер-администратор — отдельный существующий механизм.

Команда работает только при **полностью пустой таблице пользователей**, даже если каталог уже заполнен. Повторный запуск или наличие любого пользователя приводит к отказу с ненулевым кодом завершения. Ни пароль, ни роль, ни другие поля существующих пользователей не меняются. Проверка и вставка выполняются в транзакции с блокировкой таблицы: одновременный запуск не создаст второго администратора.

## Действующий магазин / импортированная БД

Не запускайте bootstrap для восстановления доступа: это не сброс пароля и не повышение прав существующего пользователя. Пользуйтесь существующей учётной записью администратора и штатным управлением пользователями. Если пользователей уже зарегистрировали, но администратора нет, владелец может использовать уже предусмотренный защищённый доступ супер-администратора для создания отдельного администратора через админку. Не удаляйте пользователей, чтобы обойти отказ команды.

Ранее созданный администратор со старым стандартным паролем **не исправляется автоматически** этим обновлением. Владелец должен отдельно заменить такой пароль штатным способом. Отзыв старых сеансов — отдельная мера; перезапуск PM2 сам по себе не отзывает сеансы в БД.

## Несколько магазинов под PM2

Изменения в Replit не обновляют внешние магазины автоматически. Для **каждого** магазина:

1. Убедитесь, что ранее внесённые аварийные исправления на сервере сохранены в репозитории и не будут затёрты обновлением.
2. Уточните каталог, имя процесса PM2 и целевую БД. Не предполагайте, что магазины используют одну БД. Перед bootstrap проверьте окружение именно SSH-команды: оно не получает настройки из PM2 автоматически.
3. Обновите код привычным способом, установите зависимости и выполните `npm run build`. Это исправление не меняет схему БД и не требует миграции.
4. Перезапустите **только нужный процесс**, не `all`:

   ```bash
   pm2 restart ИМЯ_ПРОЦЕССА --update-env
   pm2 logs ИМЯ_ПРОЦЕССА --lines 30
   ```

5. Проверьте вход с существующими данными. Для действующего магазина bootstrap не нужен. Для нового магазина выполните команду из его каталога до открытия сайта.

Не добавляйте bootstrap в PM2, deploy-скрипт, post-merge или автозапуск. Он предназначен только для однократного явного действия владельца.

## Проверка разработчиком

`npm run test:bootstrap` требует локальные `initdb` и `pg_ctl`. Тесты создают одноразовый PostgreSQL-кластер в `/tmp`, применяют текущую схему и удаляют кластер после завершения. БД магазинов и реальные секреты не используются.
