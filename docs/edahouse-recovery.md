# Восстановление eDAHouse на новом внешнем сервере

## Что подготовлено

Исходник — `attached_assets/dump_1794827013716.sql`, данные магазина
с изменениями до 27 октября 2025 года. Более поздние майские дампы другой
ветки разработки НЕ использованы.

Восстановление выполняется только в одноразовом PostgreSQL на Unix-сокете
в `/tmp/ordis-recovery-*`, без подключения к БД Replit или к внешним БД.
Пароли, роли пользователей, исходные поля, суммы заказов и связи сохраняются.
Новые таблицы писем и платежей пустые: исторические заказы не переотправляются.

Команда подготовки из оригиналов:

```bash
node scripts/prepare-edahouse-recovery.mjs --prepare
```

Результат записывается в игнорируемую приватную папку
`generated-artifacts/edahouse-recovery`. Не добавляйте её в Git.
Это одноразовое восстановление внешнего магазина, не механизм резервирования
управляемой базы Replit.

## Перед установкой

1. Установите актуальную исправленную версию PostgreSQL 16 и клиента `psql`
   не ниже 16.10, Node.js совместимой версии (проект использует Node.js 20),
   Nginx, PM2. Для новых установок выбирайте поддерживаемый безопасный Node.js
   и проверяйте сборку; не используйте архив старого кода как актуальную версию.
2. Создайте ОТДЕЛЬНУЮ пустую БД и пользователя PostgreSQL для магазина.
   Не используйте БД другого магазина.
3. Загрузите актуальный проверенный код из GitHub, включая исправление
   пересчёта ограничений количества в checkout.
4. Не запускайте приложение, пока не импортирована восстановленная БД.
   Иначе может сработать инициализация пустой БД.
5. Скопируйте комплект восстановления вне публичной папки сайта. Он содержит
   личные данные, хэши паролей и старые почтовые настройки. Права — только владельцу.
   Оригинальный ZIP с `.env` не публикуйте и не размещайте в web-root.

## Импорт (только в пустую БД)

Пример ниже предполагает БД `edahouse` и роль `edahouse_app`.
Если вы выбрали другие имена, замените их в командах.
Пароль вводится в приглашении `psql`, не в команде и не в чате.

```bash
cd /ПУТЬ/К/РАСПАКОВАННОМУ/КОМПЛЕКТУ
sha256sum -c SHA256SUMS

psql -X -W -h 127.0.0.1 -U edahouse_app -d edahouse \
  -Atc "SELECT count(*) FROM pg_tables WHERE schemaname='public';"
```

Последняя команда должна вернуть `0`. Если не ноль — остановитесь:
ничего не удаляйте и не импортируйте поверх существующих данных.

```bash
psql -X -W -h 127.0.0.1 -U edahouse_app -d edahouse \
  --set=ON_ERROR_STOP=on --single-transaction -f edahouse-restored.sql
```

Этот файл уже обновлён под код проекта. Не нужно повторно запускать
`schema-upgrade.sql`, `migration_full.sql`, `db:push` или старые миграции.
`schema-upgrade.sql` приложен для аудита именно этого исходного дампа;
это не универсальная миграция всех магазинов.

## Изображения

В каталоге приложения не должно быть чужой папки `uploads`.
Перед распаковкой проверьте назначение:

```bash
tar -tzf uploads.tar.gz | head
tar -xzf uploads.tar.gz -C /ПУТЬ/К/ПРИЛОЖЕНИЮ
```

Должны получиться `uploads/images`, `uploads/optimized`,
`uploads/thumbnails`. Владельцем файлов должен быть пользователь приложения;
не назначайте права `777`. Сохранены все 105 ссылок на файлы из БД.

## Окружение и запуск

Перенесите `.env` приватно и проверьте настройки нового сервера:
`USE_NEON=false`, `PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD`, `PGDATABASE`,
`PORT`, `SESSION_SECRET`, адрес магазина и настройки провайдеров.
Не копируйте параметры подключения потерянного сервера без проверки.
Если старый SESSION_SECRET недоступен, задайте новый — это потребует
повторного входа. Не передавайте секреты в чат или GitHub.

На первом запуске отключите инициацию онлайн-платежей:
`PAYMENT_HYP_ENABLED=false`, `PAYMENT_GROW_ENABLED=false`,
`PAYMENT_ALLPAY_ENABLED=false`, `PAYMENT_PAYME_ENABLED=false`.
Возвращайте нужные провайдеры только после проверки договора/настроек.

Из папки приложения:

```bash
npm ci
npm run build
# Первый запуск — в закрытом от посетителей окружении:
npm start
```

Nginx направляется на порт из `.env`. Сначала разрешите доступ только себе,
проверьте HTTPS и домен через hosts, и лишь затем открывайте магазин.
Не запускайте два процесса магазина с общей БД.

После проверки остановите пробный процесс и настройте PM2:

```bash
pm2 start npm --name edahouse -- start
pm2 save
```

Не запускайте эту команду, если процесс `edahouse` уже существует:
для существующего процесса используйте его проверенную конфигурацию.
Настройте автозапуск PM2 под нужным пользователем сервера.

## Контроль перед открытием

- 94 товара, 6 категорий, 62 заказа, 304 позиции, 24 пользователя.
- Публичный каталог показывает 84 товара: в исходнике у 10 товаров выключен
  флаг активности. Эти флаги сохранены; это не потеря товаров при восстановлении.
- В БД 4 администратора: владелец должен проверить их и отдельно согласовать
  отключение лишних и смену паролей. Пароли/права при подготовке не менялись.
- Каталог, изображения, цвета, логотип, баннеры, языки.
- Вход в админку (без обхода авторизации), права сотрудников.
- Тестовый заказ с оплатой наличными в закрытом окружении.
- Почтовые настройки проверять отдельно. Тестовый заказ может отправить письмо
  на сохранённый адрес администратора — сначала согласуйте получателей.
- Очередь писем сразу после импорта пустая, старые письма не переотправляются.
- Старые записи сессий относятся к историческому бэкапу; до открытия магазина
  отдельно согласуйте завершение всех старых сеансов. Не удаляйте пользователей.
- Данные после даты исходного бэкапа не восстановлены.
- После открытия настройте внешние резервные копии БД, uploads и конфигурации.

## Что подтверждает verification.json

Полный импорт исходника; добавление недостающей структуры; побайтовое сравнение
значений всех исходных колонок до/после (без вывода данных); чтение всех колонок
текущей схемы; тест INSERT заказа/позиции/очереди с ROLLBACK; отсутствие исторических
писем/платежей в новых очередях; повторный импорт итогового SQL и сравнение дампов;
проверка наличия всех ссылочных изображений. Контрольные суммы связывают комплект
с исходными файлами. Это не подтверждение установки на удалённом сервере.
