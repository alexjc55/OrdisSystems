# Проверка подтверждений платежей

## Что считается доказательством

Известный покупателю token, код транзакции или переход на страницу успеха сами
по себе не подтверждают оплату. Заказ создаётся только после проверки источника,
суммы, магазина и идентификаторов платежа. Ошибка проверки не переводит платёж
в `failed` и не затирает уже подтверждённый заказ.

| Провайдер | Проверка |
| --- | --- |
| HYP, включая `/hyp/callback` и `/hyp/webhook` | Серверный `APISign/VERIFY` со своими KEY/PassP/Masof, полным набором подписанных параметров в исходном порядке, CCode=0, Order, Amount и Id. HTML вместо результата не принимается. |
| AllPay | Уведомление: SHA-256-подпись всех полей со своим API key, order_id, сумма, ILS, status=1. Возврат браузера: подписанный запрос `paymentstatus` от магазина. Сохранение карты и chargeback-события не считаются новым платежом. |
| Grow | Если при создании сохранена пара processId/processToken: серверный `getPaymentProcessInfo` с pageCode магазина, совпадение пары, статуса, суммы и transactionId. Для старой пары transactionId/transactionToken: `getTransactionInfo` с проверкой description/token, суммы и статуса. |
| Старый контракт Grow без этих идентификаторов | Только серверное уведомление на индивидуальный секретный notifyUrl, назначенный при создании платежа. Проверяются сумма, token, код транзакции и статус, если он передан. |
| PayMe с имеющейся конфигурацией seller MPL | Только серверное уведомление на индивидуальный секретный sale_callback_url: точный payme_sale_id из ответа generate-sale, transaction_id/token, цена в агоротах, ILS, успешный тип события, status_code=0, отсутствие token-sale. |

Секрет notifyUrl — случайное 256-битное значение, отдельное для каждого платежа.
Он передаётся только серверу провайдера, не successUrl, не браузеру и не API
опроса состояния. Все адреса уведомлений и возврата строятся только из
доверенного HTTPS-origin: `REPLIT_APP_URL`, иначе первого HTTPS-origin из
`ALLOWED_ORIGINS`. В режиме development допустим HTTPS-домен этого Replit из
управляемой переменной `REPLIT_DEV_DOMAIN`; это не production-адрес.
Host, Origin и forwarded-заголовки запроса не используются. Если доверенный
адрес не настроен, инициация останавливается до сохранения сессии и запроса
провайдеру: иначе сам секрет мог бы уйти на сайт атакующего.
Это аутентификация канала уведомлений, **не** независимый
запрос состояния платежа. Для PayMe текущая конфигурация не содержит Partner
client key и merchant secret, необходимые для документированных get-sales и
MD5-подписи. Нельзя выдумывать подпись из seller MPL или считать известный sale ID
доказательством оплаты. Переход браузера в этих потоках лишь возобновляет
имеющийся опрос состояния; заказ завершает проверенное серверное уведомление.

Публичный ответ настроек отдаёт только активный провайдер и признак доступности,
без платёжных ключей. Полные настройки остаются доступны администратору.
Без этого посетитель мог бы самостоятельно подписывать уведомления AllPay.

## Суммы и J5

В момент создания сохраняются сумма с резервным буфером, режим J5, отпечаток
учётных данных магазина и серверные идентификаторы сессии. Изменение режима J5
или буфера не меняет ожидаемую сумму уже созданного платежа. Смена ключа или
магазина, напротив, требует повторной проверки у провайдера.

Grow J5 (`statusCode=11`) проверяется как резерв, не обычный платёж
(`statusCode=2`), и **никогда** не вызывает approval. Approval остаётся отдельным
подтверждением получения уведомления; неизвестный результат нельзя автоматически
повторять. См. `grow-approval-reconciliation.md`.

HYP Amount передаётся в ILS, не в агоротах. Для новых платежей принимается ровно
сохранённая сумма. Для HYP-платежей без нового контекста допускается также ровно
историческая сумма, которую прежний код отправлял в 100 раз больше: обязательно
с успешным удалённым VERIFY. Это не разрешение недоплаты и не ослабление проверки
новых платежей.

## Установка на внешние магазины

1. Изменения в Replit не обновляют внешние PM2-магазины.
   Проверить, что для выбранного магазина настроен правильный HTTPS
   `REPLIT_APP_URL` либо HTTPS-origin в `ALLOWED_ORIGINS` (как для восстановления
   пароля и писем). Не брать адрес из заголовков входящего запроса.
2. До переключения версии завершить текущие платёжные сессии. Особое внимание
   старым Grow/PayMe-платежам, у которых нет сохранённых идентификаторов для
   удалённой сверки или индивидуального notifyUrl. Их подлинность нельзя
   восстановить из известного покупателю token; сверять конкретный платёж у
   провайдера, не запускать массовое создание заказов или approval.
3. После ранее необходимых миграций применить к базе **каждого выбранного
   магазина** `migrations/0012_payment_verification.sql` перед запуском нового
   кода. Она только добавляет nullable JSONB-столбец; не меняет строки, товары,
   заказы, пользователей или пароли. Не использовать `drizzle push --force`.
4. Не запускать одновременно старые и новые обработчики платежей: старые ещё
   доверяют поддельным уведомлениям. Перезапустить выбранный магазин после
   миграции и обновления.
5. Проверить один тестовый платёж и повтор уведомления для используемого
   провайдера. Не проводить реальные списания без согласования владельца.
6. Платёжные ключи раньше могли попадать в публичные настройки. Согласовать
   их замену с владельцем/провайдером; смена ключа может прервать проверку старых
   сессий. Автоматически ключи, учётные записи и сессии не меняются.

Если старое уведомление нельзя подтвердить, платёж остаётся `pending`: оно не
считается ни успешным, ни окончательно неуспешным. Нужна сверка у провайдера,
а не возврат к проверке только token/success. После обновления новые платежи
получают совместимый проверяемый канал сразу при создании.

## Проверка

`npm run test:payments` запускает изолированный UTF-8 PostgreSQL и тесты реальных
обработчиков, финализации, очереди писем и верификаторов. Внешние ответы
провайдеров заменены проверяемыми тестовыми ответами; реальные провайдеры и
платёжные аккаунты этими тестами не вызываются. Покрыты подделки с известным
token, подпись, сумма, магазин, идентификаторы, успешные события, legacy HYP,
смена активного провайдера, J5 и идемпотентность заказов/писем/approval.

В базе приложения этого Replit применены подготовленные дополнительные
миграции 0007–0012: предыдущие столбцы и таблица очереди отсутствовали, из-за чего
опрос платежа вызывал сбой сервера. Эти миграции не удаляют данные и не ставят
старые письма в очередь. Установка на внешние магазины здесь не выполнялась.
